# 一个 skill 源目录 + 三份生成的客户端副本，差异只允许出现在 `references/scheduling.md`

仓库目前只发布 `.dsh/skills/academic-digest/`，而三家 Agent 的扫描根互不相通：Claude Code 只读
`.claude/skills/`，Codex 只读 `.agents/skills/`，DSH 读 `.dsh/skills/`（rank 100）与 `.agents/skills/`
（rank 200）。开源后别人克隆下来，三家里有两家看不见这个 skill。同时，本项目与常见的"技能即目录"
项目不同：入口脚本与 `academic_digest/` 包原来在仓库根，只拷走 `academic-digest/` 目录会得到一个
"能被发现但一跑就找不到脚本"的 skill。围绕"用软链共享一份"还是"每家一份真实文件"，以及要不要
用插件分发，2026-10-23 的调研（`docs/research/06-distribution-and-scheduling.md`）确认：软链在
Windows 的 `core.symlinks=false` 克隆里会退化成文本文件；插件对单 skill 会让触发名变成
`/academic-digest:academic-digest`，而 Codex 侧根本没有 `plugin install` 命令。因此决定：
**`skills/academic-digest/` 是唯一源目录，代码（`scripts/` + `academic_digest/`）搬进其中使其自包含；
`.dsh/skills/`、`.claude/skills/`、`.agents/skills/` 下提交三份生成的副本，三份之间只允许
`references/scheduling.md` 不同，其余逐字节一致；副本由 `scripts/sync-skills.sh` 生成、
`scripts/check-skills.sh` 在 CI 里校验。** 换来的是每个目录都能被单独拷走并在对应客户端里直接工作，
代价是仓库里多两份代码副本，必须靠生成器与校验脚本防漂移。

**Decision**：

- 源目录：`skills/academic-digest/`，含 `SKILL.md`、`references/{digest,setup}.md`、
  `references/scheduling/{dsh,claude,codex}.md`、`scripts/`、`academic_digest/`；仓库根的
  `scripts/` 只保留开发工具（check / check-docs / sync / check-skills / review-patch）。
- 差异边界：三份客户端方案写在 `references/scheduling/{dsh,claude,codex}.md`（只对维护者可见、不随
  副本分发），同步时把对应那份落成副本内的 `references/scheduling.md`，并在文件头留一行
  `<!-- generated by scripts/sync-skills.sh -->`。
- 同步与校验：`sync-skills.sh` 拷整棵树、排除 `references/scheduling/`、再写入对应 `scheduling.md`；
  `check-skills.sh` 把三份同步结果生成到临时目录，与已提交副本逐字节比较（每份的
  `references/scheduling.md` 也按该客户端变体校验；三份之间唯一允许不同的是这个文件），并额外
  断言每份里出现该客户端的启动命令。
- 运行时数据不跟着 skill 走：`config.yaml`、`secrets.env`、`out/`、`state/` 永远留在仓库根，
  命令形态是 `cd <repo> && python3 <skill>/scripts/collect.py --config config.yaml`。入口脚本用
  `sys.path` bootstrap 指向自己所在 skill 目录，因此克隆后不装包也能跑。
- 分发形态：只做 CLI。`scripts/run-daily.sh <claude|codex>` 是 Claude Code 与 Codex 共用的无人
  值守入口；DSH 由看板卡直接起会话，不经过该脚本。
- 仓库标记：`.gitattributes` 把三份副本标为 `linguist-generated`，让 GitHub 折叠它们并排除出语言统计。
- 不在仓库内使用软链：不提交根 `SKILL.md` 软链、不用软链共享三份副本、不在仓库根保留
  `scripts/*.py` 薄壳——三者都会在"三家各自独立"的前提下重新引入共享路径。用户级安装
  （`~/.claude/skills/`、`~/.agents/skills/`、`~/.dsh/skills/`）仍可用软链指向仓库内副本。

**Considered options**：软链共享一份（否决：Windows 克隆退化、且三份客户端定时方案无法各写各的）；
插件/marketplace 分发（否决：单 skill 命名空间化、Codex 无 CLI 安装）；代码留仓库根、只复制文档
（否决：副本不自包含，`cp -r` 出来的 skill 跑不起来）；副本不入库、克隆后跑脚本生成（否决：克隆完
直接打开 Agent 的两家看不到 skill，且用户不会在读 README 前先执行 setup）。

**Consequences**：任何 skill 文档或代码改动只改源目录，忘记同步就是 CI 红——这是有意的失败模式。
仓库里因此有三份 `academic_digest/`（约 8335 行 × 3）；PR diff 里会看到三份，`linguist-generated`
只负责折叠与语言统计，不减少磁盘占用。副本禁止手改：本地编辑 `.claude/skills/...` 会在下次
`sync-skills.sh` 被覆盖、并被 `check-skills.sh` 判红。新增一个客户端只需加一份
`references/scheduling/<client>.md`，再在同步脚本的客户端映射与校验测试的 `COPIES` 里各补一行，
不需要改生成逻辑。`GLOSSARY.md` 只增加 `skill` 一条词条（"遵循 Agent Skills 格式的目录包"）；
"源目录 / 副本 / 同步"是仓库结构词，只写在 `docs/`
里，不进入领域词汇表。
